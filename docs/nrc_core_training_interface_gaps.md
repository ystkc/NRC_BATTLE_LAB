# nrc_core 训练接口：待协商项

本文记录 docs/nrc_core_training_interface.md 没有完全定义、或当前旧规则引擎尚不能严格满足的内容。实现先采用下方的临时约定；上层开发者确认后，应同步更新接口契约、版本号和验收用例。

## 1. 接口对象的精确 schema

契约给出了 CoreManifest、Decision、LegalAction、Observation、Transition 的字段方向，但没有定义：

- setup 的完整 JSON schema、必填字段、默认初始生命/能量、队伍长度和初始上场索引；
- LegalAction.payload 中技能、选择项、目标、道具组合和次数的精确字段类型；
- Observation.data 的公开字段、隐藏字段、事件字段和历史帧拼接规则；
- Transition.events 的事件类型、字段以及事件是否属于公开信息；
- Transition 是否应包含 truncated、折扣因子或终局后的最后观测；
- Decision.phase 的完整枚举，以及强制换人、传动、回合结束之间的阶段顺序。

当前实现的临时约定是：setup 接受现有 BattleRequest JSON 的 own_team、opponent_team、shared 结构；动作 payload 使用 SideTurnInput JSON；观测分为完整己方队伍和只含战斗公开状态的对手队伍。快照使用带 manifest 校验的内部 pickle payload，后续应确定正式跨进程格式。

## 2. 可见性边界

契约要求隐藏对手技能、奉献、性格等信息，但没有逐字段列出“公开/己方私有/核心全知”边界，尤其未明确：

- 对手精灵名称、属性、最大生命、能量、特性是否在上场或首次展示后公开；
- 对手替补队伍的数量、名称、当前生命和已知技能如何逐步揭示；
- 印记、天气、魔力、状态层数和冷却是否始终公开；
- 特性触发事件应在观测中公开到什么粒度。

当前实现只把己方完整运行态放入观测；对手只输出队伍槽位、上场标记、名称/属性、生命/能量、状态、冻结/萌化等战斗状态，不输出对手技能、特性、能力状态或完整数值属性。

## 3. 尚未能严格满足的 P0 项

- 核心已将已审计的随机技能、特性、目标选择和同速判定改为调用作用域 RNG；后续新增随机路径仍必须继续通过 src.rng 接入，不能重新使用模块级 random。
- 旧核心中仍有少数强制换人路径直接写入 current_* 占位；训练适配器已禁止死亡后的普通自动补位，但所有技能/特性的强制换人路径仍需逐项审计。
- 回合开始效果已在 new_game 和每次新回合决策前预结算，并用状态标记避免正常回合重复结算；需要上层确认“回合开始后、等待双方选择前”是否就是正式公开节点。
- 目前 P0 支持已实现的巧变、魔术帽、时间特性、血脉属性输入、愿力强化、进化之力、光合治愈和带 metadata.gulu_ball 的契约形状；血脉属性只作为阵容信息和技能池信息传入，不参与属性克制计算。仍会拒绝选择类技能、未上线共鸣魔法和随机奉献等尚未形成接口契约的阵容，遇到这些内容会抛 UnsupportedMechanicError。

## 4. 规则语义仍需确认

- 力竭导致魔力扣减的具体对象、扣减时机和与同时终局的优先级；
- MP 归零与全队倒下的终局判定优先级，以及平局是否可能出现；
- 强制换人期间是否允许同时结算入场特性、印记和天气；
- 冻结致死后是否立即生成换人决策，还是先完成当前回合剩余结算；
- 选择类技能的合法选项、目标枚举、选项是否可能依赖对手隐藏信息；
- 选择类技能的选项字段、合法目标枚举和上层如何把选择传入 SideTurnInput；
- 巧变技能的替换范围与抽取分布是否以当前数据库描述为最终规范；当前实现为动作结算后、回合结束前替换，替换技能从下一决策节点开始可用；
- 随机奉献的抽取分布、抽取历史字段和快照恢复要求；
- “使用/应对计数”中哪些是技能计数，哪些是全局/阵营计数，以及切换精灵后的继承规则。

## 5. 版本与快照

契约要求兼容版本拒绝和完整恢复，但没有规定 hash 算法、快照跨 Python 版本兼容性、是否允许非可信进程导入快照。当前实现：

- rules_version 是属性克制表、回合顺序、游戏规则 CSV 以及已纳入规则的核心实现文件的 SHA-256 前 16 位；
- catalog_version 是 data/nrc_wiki.db 的 SHA-256 前 16 位；
- action_version、observation_version 当前为 1；
- 快照 payload 是内部 pickle，仅适合受信任的同版本 Python 进程，不应直接作为长期数据格式或跨语言协议。

## 6. 建议的协商结果

请上层开发者优先确认第 1、2、4 节，尤其是 setup/observation/action 的正式 schema 和公开信息边界。确认后应：

1. 更新主接口文档并提升相应版本号；
2. 将本文件中已确认项目移入正式契约；
3. 为每个支持的机制补一个最小真实阵容验收用例；
4. 在 RNG 注入完成前，不把当前适配器标记为支持无锁多 worker 并行。
